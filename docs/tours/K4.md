# Code Tour — K4: Executors (threads, asyncio, subinterpreters), gilwatch and the planted race

> **Commit:** the final commit of branch `milestone/k4-concurrency` (line numbers below match it) · **Time needed:** ~2 h for the tour, plus the K4 primers · **Milestone spec:** [K4](../milestones/K4-concurrency-backends.md) · **Lab report:** [K4](../labs/K4-concurrency.md)

Until K4 every worker ran one job at a time. Now a worker can run up to `worker.executor_concurrency` jobs at once in three new ways, and the rest of Kiln barely notices: the master already counted slots, and the channel was already safe for several senders. Follow one `run` message into each executor and back, then see the two tools K4 builds for the free-threaded world: gilwatch and the race demo.

## The map

```
  master ──run──▶ worker main thread (reads the channel, never runs tasks itself except under sync)
                    executors.make_executor(config, app)
                    ├─ sync          run_task inline                      capacity 1
                    ├─ threads       ThreadPoolExecutor "kiln-job_N"      capacity C
                    ├─ asyncio       loop thread "kiln-loop"              capacity C
                    │                  async task: asyncio.timeout → timed_out
                    │                  sync task: to_thread "kiln-tothread_N"
                    └─ interpreters  InterpreterPoolExecutor              capacity C
                                       _run_in_interpreter(app_spec, sys_path, labs, task, JSON...)
                  on_done(result) from any thread
                    ──▶ WorkerState.lock: count + recycle decision + `retiring`
                    ──▶ Channel.send (lock around sendall) ──▶ master
  master: asyncio workers' timer = timeout_s + jobs.cancel_grace_s; a kill → collateral worker_lost
  free-threaded builds: gilwatch on sys.meta_path in master and workers → `gil_reenabled`
```

## Stop 1 — `src/kiln/worker/executors/base.py:L31` (`Executor`) and `L136`/`L160` (`value_result`, `run_task`)

- **Look at:** the protocol's docstring: "call on_done exactly once per run, from any thread". Then the helpers every executor shares: an unknown task, an exception, a value that must survive `json.dumps(..., allow_nan=False)`.
- **This code answers the question:** "How can four very different executors report results identically?" They all build their `Result` with these helpers.
- **Notice:** K4 kept K1's `submit(run, on_done)` shape (ADR-037 §1): the per-job callback *is* the spec's "result sink".

## Stop 2 — `src/kiln/worker/channel.py:L61` (`Channel.send`) and `worker/main.py:L344` (`finished`)

- **Look at:** `send` encodes the frame *outside* the lock and sends it *inside*. Then `finished`: count, decide about recycling and announce `retiring` all happen under `state.lock`.
- **This code answers the question:** "What breaks when several threads finish jobs at the same time?" Two `sendall`s could interleave bytes and corrupt the framing, and two `jobs_done += 1` could lose an update.
- **Tested by:** `tests/unit/test_k4_worker_pieces.py::test_concurrent_senders_never_interleave_frames` (8 threads × 1,000 frames) and `tests/integration/test_worker_counters.py` (2,000 jobs on 8 threads, exactly 2,000 counted on 3.15t).

## Stop 3 — `src/kiln/worker/executors/threads.py:L56` (`_run`) and `L80` (`submit`)

- **Look at:** `submit` returns at once; a `kiln-job_N` thread runs `_run`, which catches even `BaseException` so that every run gets exactly one answer. The in-flight count changes only under `self._lock`.
- **This code answers the question:** "Why didn't CPU-bound jobs speed up on 3.15 but did on 3.15t?" Same code, different build: on the GIL build only one of these threads runs Python at a time (lab table (a)).

## Stop 4 — `src/kiln/worker/executors/asyncio_exec.py:L47` (`__init__`) and `L66`, then `_run_job`

- **Look at:**
  - The loop lives in its own thread (`kiln-loop`); `run_coroutine_threadsafe` is the one thread-safe way in.
  - L66 replaces the default `to_thread` pool with one sized to the capacity.
  - In `_run_job`, async tasks get `asyncio.timeout(...)` (→ `timed_out=True`), while sync tasks get none.
- **This code answers the question:** "Why can the asyncio executor survive a timeout, but threads can't?" Cancellation in asyncio is *cooperative*: the task stops at its next `await`. A thread can't be stopped, so cancelling the `await` around `to_thread` would leave the thread running on a slot the master thinks is free.
- **And the other half:** `master/dispatcher.py:L66-L70` gives asyncio workers `timeout_s + cancel_grace_s` before the hard kill, so only uncooperative tasks (`labs.block_loop`) get killed. `tests/integration/test_asyncio_timeouts.py` shows both cases.

## Stop 5 — `src/kiln/worker/executors/interpreters.py:L50` (`_run_in_interpreter`) and `L159` (`done`)

- **Look at:**
  - What crosses into the subinterpreter is only strings and a bool: the app spec, `sys.path` as JSON, the task name, the args as JSON.
  - Inside, the shim imports the app once per interpreter (`_APPS`) and answers with a JSON string.
  - `done` turns that back into a `Result`, and logs `interp_import_failed` for import errors.
- **This code answers the question:** "What's shared between subinterpreters?" Almost nothing: each has its own copy of every module, as `labs.interp_probe` shows (same pid, different module objects).
- **Notice:** errata E-25. The stdlib's `_tracemalloc` refuses to load in a subinterpreter, and Kiln's own lab tasks imported it. That's why `kiln/labs/preload.py` imports tracemalloc inside a function.

## Stop 6 — `src/kiln/worker/gilwatch.py:L154` (`GilWatchFinder`), `L121` (`create_module`), `L247` (`_leave`), `L372` (`install_for_process`)

- **Look at:** the same delegate-and-wrap pattern as K3's gcwatch layer B, watching `sys._is_gil_enabled()` instead of `gc.isenabled()`. `create_module` is wrapped too, because a C extension's GIL decision happens while its module object is created. `_leave` blames the *innermost* import that flipped the GIL.
- **This code answers the question:** "Which dependency silently made my free-threaded server single-core again?" The log line names the module, the chain of imports that led to it, and the `.so` file.
- **Tested by:** `tests/unit/test_gilwatch.py`, which simulates a flip on every build. The real test against the C extensions, `tests/integration/test_gil_reenabler.py`, needs a C compiler.

## Stop 7 — `labs/k4/race_demo.py:L35` (`RacyStats`) and `L82` (`trial`)

- **Look at:** two lines that each read, change and write, and a `Barrier` so eight threads start at the same instant.
- **This code answers the question:** "Is my code thread-safe because it never crashed?" No. On 3.15t, `RacyStats` loses most of its updates and never raises an error. On 3.15 the dict line loses updates too, because CPython can switch threads right after `d.get(...)` returns (errata E-27).

## Checkpoint quiz

1. Why does the `threads` executor wrap `run_task` in `except BaseException`, when `run_task` already catches `Exception`?
   <details><summary>Answer</summary>

   A task can raise something that isn't an `Exception`, such as `SystemExit` from `sys.exit()`. In a pool thread nobody would ever see it, and the master would wait for an answer until the job's timeout. Every `run` must get exactly one result.

   </details>
2. The asyncio executor runs a plain `def` task with `asyncio.to_thread`. Why not call it directly on the loop?
   <details><summary>Answer</summary>

   A plain function never awaits, so while it runs the loop can't do anything else: every other job on the loop, and every timeout, would wait for it. Running it on a pool thread keeps the loop free.

   </details>
3. Why does the interpreters shim take the main interpreter's `sys.path` as an argument?
   <details><summary>Answer</summary>

   A subinterpreter starts with Python's default import path. `kiln serve` added the current folder (and `app.pythonpath`) to the *main* interpreter's `sys.path` only, so without copying it across, `import examples.demo` fails inside the subinterpreter.

   </details>
4. gilwatch is installed in the master *and* in each worker. A forked worker inherits the master's watch. What would go wrong if the worker installed a second one anyway?
   <details><summary>Answer</summary>

   Two finders would sit on `sys.meta_path`, both wrapping every import, so each GIL flip would be reported twice. `install_for_process` keeps one watch per process (the `_ACTIVE` global).

   </details>
5. On 3.15, `count += 1` from 8 threads never lost an update, yet the dict line lost most of them. What's different?
   <details><summary>Answer</summary>

   Where CPython may switch threads. It checks for a pending switch at backward jumps, `RESUME`, and the end of most calls, but not inside `STORE_ATTR` or `BINARY_OP`, so `+= 1` on an attribute is never interrupted on the GIL build. `d.get(...)` is a call: a thread can be paused right after it returns, before the store. When it resumes, it writes a value that's a whole time slice old (errata E-27).

   </details>
