# Code Tour — K0: Foundations (environment, tooling, first primers)

> **Commit:** the final commit of branch `milestone/k0-foundations` (line numbers below match it) · **Time needed:** ~60 min for the tour, plus ~3 h for the starter primers and notes · **Milestone spec:** [K0](../milestones/K0-foundations.md) · **Lab report:** none for K0. The [setup log](#appendix-setup-log) at the end plays that role.

K0 contains no "Kiln server" yet. It builds the **workshop**: the commands you run (`dev.sh`), the inspector that checks your machine (`kiln doctor`), the format every measurement is saved in (`records.py`), and the robot that enforces the documentation rules (`check_docs.py`). Reading this code is also your first practice at reading Python, using the notes you'll find in [`docs/python/`](../python/README.md).

## Stop 1 — `scripts/dev.sh:L32-L66` and `L185-L203`

- **Look at:** `set -euo pipefail` (L32), how `REPO_ROOT` is computed (L44), the two `export` lines for `UV_PROJECT_ENVIRONMENT` and `UV_PYTHON` (L56–57), and the `case` table at the end that maps each subcommand to what it runs.
- **This code answers the question:** "How do I run Kiln's tools the same way every time, on the right Python, without the venv landing on the slow `/mnt/c` disk?"
- **What would break without it:**
  - Without `-e`, a failed `ruff` would be ignored and `check` would print "all green" anyway.
  - Without the quotes around `"$REPO_ROOT"`, the space in `Karthik Reddy` would split the path into two words.
  - Without `UV_PROJECT_ENVIRONMENT`, uv would create `.venv` inside the repo, on 9P (ADR-003).
- **Notice:** the `check` line chains commands with `&&`, so it stops at the first failure. The header comment is a mini bash course; read it before the code.

## Stop 2 — `src/kiln/__main__.py:L20-L30` → `src/kiln/cli.py:L140-L161`

- **Look at:** `if __name__ == "__main__":` in `__main__.py`, then `main(argv)` in `cli.py`: build the parser, parse, dispatch, return an exit code.
- **This code answers the question:** "What happens between typing `kiln doctor` and the doctor code running?"
  1. The `kiln` command is a tiny script generated from `[project.scripts]` in `pyproject.toml`.
  2. That script calls `kiln.cli.main()`.
  3. `main()` uses `argparse` (see [argparse](../python/argparse.md)) to understand the words you typed.
- **What would break without it:** `main()` *returns* the exit code instead of calling `sys.exit` itself. That's what lets tests call `cli.main(["doctor", "--json"])` directly (see `tests/unit/test_cli_smoke.py`).
- **Notice:** `version_text()` (L45) is tested with a **doctest**, the `>>>` lines inside its docstring. pytest runs those lines too (`--doctest-modules` in `pyproject.toml`).

## Stop 3 — `src/kiln/doctor.py:L196-L252` (`DoctorContext` and `DoctorContext.real()`)

- **Look at:** the list of fields. That list is *everything* a check is allowed to look at: where `/proc` is, how to run a command, which platform, which Python...
- **This code answers the question:** "How can you test code that inspects the machine on a machine that is different?"
- **What would break without it:** if checks called `open("/proc/...")` or `subprocess.run` directly, the tests could only pass on a computer set up exactly like yours. With the context, tests pass a *fake* `/proc` folder and a *fake* command runner (stop 5). This pattern is called **dependency injection**: give a function what it needs instead of letting it fetch it.
- **Notice:** `real()` is a `@classmethod`, a second way to build a `DoctorContext`. The `# PY:` comment above it explains what that means.

## Stop 4 — `src/kiln/doctor.py:L549-L578` (`check_d11`) and `L858-L895` (`escalate`, `run_checks`)

- **Look at:** one complete check. It reads one `/proc` file, handles "file missing" (INFO), "0" (PASS) and anything else (WARN with a fix). Then look at `escalate`, which turns a WARN into a FAIL when you pass `--milestone`.
- **This code answers the question:** "How does `kiln doctor --milestone K5` know that ptrace matters for K5 but not for K1?" Each result carries `needed_by="K5"`, and `escalate` compares milestone numbers.
- **What would break without it:** you'd discover `ptrace_scope = 1` halfway through the K6 leak lab, as a cryptic "Operation not permitted".
- **Notice:** every check returns the same `CheckResult` shape, so `render_table` and `render_json` never need to know which check produced a row.

## Stop 5 — `tests/unit/test_doctor.py:L63-L115` (`make_context`) and `L176` (`test_missing_compiler_warns_until_k4`)

- **Look at:** `make_context` builds a fake healthy machine in a temporary folder: a pretend `/proc/sys/kernel/yama/ptrace_scope` containing `0`, a pretend `/proc/meminfo`, a pretend `scripts/dev.sh`... Each test then changes **one** thing (`replace(context, platform_name="win32")`) and checks one result.
- **This code answers the question:** "How do you prove a check works without breaking your real machine?"
- **What would break without it:** nothing visible today. But the first time someone edits a check, nothing would catch a mistake.
- **Notice:** `FakeRunner` is a dataclass whose `run` method answers commands from a table. Unknown commands get exit code 127, the shell's "command not found".

## Stop 6 — `src/kiln/bench/records.py:L264-L322` (`new_record`) and `L457-L489` (`write_record`)

- **Look at:** `new_record` captures the interpreter, host and git state automatically. `write_record` validates, writes to `<name>.json.tmp`, then `os.replace`s it into place.
- **This code answers the question:** "When K3 says 'PSS per worker was X', how do we know which Python, which machine and which commit produced X?" Every number lives in a file that also records all of that ([spec/10 §2](../spec/10-measurement-methodology.md#2-the-experimentrecord-one-json-file-per-run)).
- **What would break without it:** a crash in the middle of `write_text` could leave half a JSON file, and K9's report would choke on it. Writing to a temporary name and renaming is the standard **atomic write** trick: the rename happens all at once or not at all.
- **Notice:** `_source_location` writes `source=9p` into every record made on `/mnt/c`, so a timing benchmark run in the wrong place is visible in the data (ADR-003).

## Stop 7 — `scripts/check_docs.py:L588-L630` (`constructs_in`, `_mark`) and `L803` (`check_doc005`)

- **Look at:** how the checker finds which Python features a file uses. It doesn't search the text. It asks Python's own parser for the **syntax tree** (`ast.parse`) and walks every node: a `With` node means a `with` statement, a `JoinedStr` node means an f-string, and so on.
- **This code answers the question:** "How can a script know that `doctor.py` uses decorators, so it can demand a decorators note?"
- **What would break without it:** the promise "every Python feature used in this repo has a note" (ADR-002) would only be a promise.
- **Notice:** `_classify_node` is the construct map from the K0 spec, written as code. When K1 introduces `match` or `__slots__`, DOC005 will fail until `match-statement.md` or `slots.md` exists. That failure is intentional.

## Stop 8 — `tests/unit/test_check_docs.py:L93` (`CASES`) and `L203`

- **Look at:** for each of the 17 checks there is a *bad* mini-repository that breaks exactly that rule, and the change that makes it *good*. One parametrized test runs all 17.
- **This code answers the question:** "How do we know the checker isn't silently passing everything?" A check that can never fail proves nothing.
- **Notice:** `test_every_check_has_a_case` fails if someone adds a check without a test case.

## Reference comparison

- **Our `pyproject.toml` vs pytest's own.** [pytest's `pyproject.toml`](https://github.com/pytest-dev/pytest/blob/main/pyproject.toml), fetched 2026-11-03, keeps almost every tool's configuration in that one file too: `[tool.ruff]`, `[tool.mypy]`, `[tool.pytest]`, `[tool.coverage.*]`, plus tools we don't use (`towncrier` for changelogs, `codespell`, `pyright`, `setuptools_scm` for versions taken from git tags). The differences:
  - It builds with **setuptools**, because it needs `setuptools_scm` and package data. We use `uv_build`: a pure-Python src layout needs nothing more (spec/08 §2.1).
  - It has a `[dependency-groups]` table like ours.
  - It configures two type checkers. We deliberately use one (ADR-019).
  - The lesson: putting config in `pyproject.toml` has become the norm, so a single file tells a newcomer how the project is built and checked.
- **`check_docs.py` vs Ruff's `D` (pydocstyle) rules.** Ruff's `D` rules overlap with DOC001/DOC003: they require docstrings and check their format, but only on *public* functions. Our DOC003 also covers private and nested ones. Everything else is Kiln-specific and no general tool can know it: the four module-docstring headings, `Why:` sections, the Python ledger, primer and lab-report structure, glossary coverage, and milestone deliverables. That's why both run in `dev.sh check`.
- **`kiln doctor` vs `flutter doctor` / `brew doctor`.** All three do the same useful thing: they turn "something deep down is missing" into a short list of ✅/❌ lines, each with the exact fix command. What makes such output useful:
  - one line per check;
  - a concrete fix command rather than a description;
  - exit codes that scripts can use.
  - Our addition is `--milestone`, because a learning project has a *timeline*: Rust isn't a problem until K8.

## Checkpoint quiz

1. Why can't Kiln run on Windows directly? Name two things it needs that Windows lacks.
   <details><summary>Answer</summary>

   Kiln needs `fork()` (to copy the master into workers), `/proc` (to read memory numbers), Unix signals like `SIGHUP`/`SIGCHLD`, and cgroups (for the OOM lab). Windows has none of these, so Kiln runs in WSL2's real Linux kernel (ADR-003).

   </details>
2. What is the difference between `/mnt/c/...` and `~/` inside WSL, and why does the venv live in `~/.cache`?
   <details><summary>Answer</summary>

   `/mnt/c` is the Windows disk, reached through the slow 9P protocol. `~` is on WSL's own ext4 disk, which is fast. A venv holds thousands of small files that Python opens on every import, so it lives on ext4 (`~/.cache/kiln/venvs/py3.15`). `dev.sh` sets `UV_PROJECT_ENVIRONMENT` to arrange that.

   </details>
3. What does `uv sync --group dev` do?
   <details><summary>Answer</summary>

   It makes the virtual environment match `uv.lock` exactly. It installs the project plus the `dev` group (pytest, ruff, mypy...) and removes anything not listed. (`dev` is also the default group, set by `default-groups` in `pyproject.toml`.)

   </details>
4. In `def f(x, items=[]):`, what's the bug waiting to happen?
   <details><summary>Answer</summary>

   The default list is created **once**, when the `def` runs, and is shared by every call that doesn't pass `items`. Appending to it in one call leaves the item there for the next call. Use `items=None` and create a new list inside. See [functions](../python/functions.md).

   </details>
5. What's the difference between `"héllo"` and `"héllo".encode()`? How many bytes is the second one?
   <details><summary>Answer</summary>

   The first is a `str` of 5 characters. The second is `bytes`: the UTF-8 encoding of that text, which is **6 bytes**, because `é` takes 2 bytes in UTF-8. See [bytes-vs-str](../python/bytes-vs-str.md).

   </details>
6. What does `with open("f") as fh:` guarantee that `fh = open("f")` doesn't?
   <details><summary>Answer</summary>

   That the file is closed when the block ends, even if an exception happens inside it. With a bare `open`, an error before `fh.close()` leaks the file descriptor. See [context-managers](../python/context-managers.md).

   </details>
7. What does a decorator receive, and what does it return?
   <details><summary>Answer</summary>

   It receives a function (or class) and returns what should replace it: often a wrapper, or the original after registering it somewhere. `@d` above `def f` means `f = d(f)`. See [decorators](../python/decorators.md).

   </details>
8. What does `kiln doctor --milestone K4` do differently from `kiln doctor`?
   <details><summary>Answer</summary>

   Every ⚠️ whose `needed_by` is K4 or earlier becomes ❌, and the exit code becomes 1 if any do. A missing C compiler (needed by K4) fails; missing Rust (K8) stays a warning. It answers "am I ready to start K4?".

   </details>
9. What are file descriptors 0, 1 and 2?
   <details><summary>Answer</summary>

   stdin (input), stdout (normal output) and stderr (errors and logs). Every process starts with these three open. See [files-and-file-descriptors](../concepts/files-and-file-descriptors.md).

   </details>
10. Why does `check_docs.py` exist? What would go wrong in this project without it?
    <details><summary>Answer</summary>

    Because documentation is the product (ADR-001/026). Without automatic checks, docs drift. A function gets added without a docstring, a Python feature appears without a note, a link breaks when a heading is renamed. The learner, who can't ask the author, would hit dead ends. The checker makes "documented" part of "the build passes".

    </details>

### Mistakes made along the way (and what they teach)

- **CRLF sneaked in.** Some files were edited with a Python one-liner running on *Windows*. `Path.write_text()` translates `"\n"` into the platform's newline, which on Windows is `"\r\n"`. Ruff reported strange line numbers until the files were converted back to LF. Lesson: on Windows, write text files with `write_bytes(text.encode())` or `newline="\n"`. `.gitattributes` (`eol=lf`) makes git normalize them, and doctor D16 checks the shell scripts.
- **`$?` printed the wrong exit code.** Running `wsl.exe -d Debian -- bash -c '...; echo $?'` from Windows printed `0` even when the command had failed. WSL first hands the command line to the *login shell* (zsh here), which replaced `$?` with its own value before bash ever ran. Running the same lines from a script file showed the true exit code (`1` for `doctor --milestone K10`). Lesson: test exit codes inside a script, or escape the `$`. See [terminal-and-wsl](../concepts/terminal-and-wsl.md).
- **Ruff reformatted Markdown.** Ruff 0.17 also formats Python code blocks *inside Markdown files*. That rewrote the hand-aligned examples in the specs. The fix was `extend-exclude = ["*.md"]` in `pyproject.toml` and restoring the specs from git.
- **Snippet and fixture files.** The K0 spec talks about fixture *folders* (`tests/fixtures/check_docs/…`, `tests/fixtures/boundaries_bad/`). The tests build those tiny repositories in pytest's `tmp_path` instead, from strings in the test file (`CASES` in `test_check_docs.py`, `test_a_planted_bad_import_is_caught`). One file then shows each bad and good example side by side, and nothing stray gets left in the repo. The behaviour required by AC-0.6 and AC-0.8 is the same.
