# Code Tour — K3: Copy-on-write, the GC modes, and "who re-enabled the GC?"

> **Commit:** the final commit of branch `milestone/k3-cow` (line numbers below match it) · **Time needed:** ~2 h for the tour, plus the K3 primers · **Milestone spec:** [K3](../milestones/K3-copy-on-write.md) · **Lab report:** [K3](../labs/K3-cow.md)

K3 adds no new server feature. It adds *measurement* (how much memory is really shared), *control* (four ways to handle the garbage collector around fork) and *detection* (catching code that switches the GC back on). Follow a preloaded object graph from the master into four forked workers, watch reading and collecting copy its pages, and see where each GC mode intervenes.

## The map

```
  master (fork) / forkserver
    gcmodes.apply_parent_early(mode)        disable / threshold(0) BEFORE anything is loaded
    [gcwatch installed if labs.gc_watch]    layers A (shim) + B (import hook) + C(2) (sentinel)
    load the app, preload.ensure_graph(300) the 300 MiB graph: shared by every child
    launch/fork.py fork_child:
      gcmodes.before_fork(mode)             freeze (once per process)
      os.fork() ───────────────────────────▶ worker
                                              gcmodes.apply_child_early(mode)  enable under freeze
                                              [own gcwatch; heartbeat thread polls = C(1)]
                                              labs.touch_preloaded → refcount writes → page copies
                                              labs.churn / labs.gc_collect → GC header writes
  outside the server:
    labs/k3/sampler.py, kiln mem ──▶ procfs.read_smaps_rollup(pid) ──▶ Shared / Private_Dirty / PSS
```

## Stop 1 — `src/kiln/memory/procfs.py:L106` (`SmapsRollup`) and `L163` (`parse_smaps_rollup`)

- **Look at:** the eleven fields, the `uss` and `shared` properties, and the `# GOTCHA:` that the kernel's "kB" means KiB.
- **This code answers the question:** "How much of this worker's memory is really its own?" `private_dirty` grows exactly when copy-on-write copies happen; `pss` divides shared pages fairly, so Σ PSS is the true total.
- **Tested by:** `tests/unit/test_procfs.py` (fixture text, missing lines) and `tests/integration/test_procfs_live.py::test_writing_shared_pages_in_a_child_grows_its_private_dirty`, which forks, writes 64 MiB, and sees Private_Dirty grow by at least that much.

## Stop 2 — `src/kiln/memory/memtable.py` (`collect`, `render_text`) and `cli.py` `_cmd_mem`

- **Look at:** how `collect()` labels processes from the *tree* (`children_of`), not the command line: a forked worker's command line is identical to its master's.
- **Try it:** `kiln mem --children-of <master pid>` while the K3 lab runs. Watch the Σ PSS column grow while Σ RSS doesn't. The footnote says why.

## Stop 3 — `src/kiln/memory/gcmodes.py:L65`, `L87`, `L110` (the three hooks)

- **Look at:** the table in the module docstring, then each hook. `apply_parent_early` runs before the app and the graph exist; `before_fork` freezes; `apply_child_early` re-enables the GC under `freeze` (but not under spawn, where nothing is shared).
- **This code answers the question:** "Where exactly does each step of the freeze recipe have to happen, and why?" The docstrings give the reason for each placement.
- **Notice:** the `_FROZEN` guard in `before_fork`. Freezing before *every* fork was a real bug on 3.15t (lab report §7). The fix is one dict and one `if`.

## Stop 4 — the hook points: `master/arbiter.py:L405-L440` (`_apply_k3_settings`, `_build_preload_graph`), `launch/fork.py:L75`, `launch/forkserver_main.py:L306`, `worker/main.py:L246-L262`

- **Look at:** the order in each process: watch → parent-early → app → graph (master/forkserver); child-early → watch → app → graph (worker, which builds its own graph only under spawn).
- **This code answers the question:** "Who is the *parent* whose memory gets shared?" Under fork it's the master, under forkserver it's the forkserver, and under spawn there is none.

## Stop 5 — `src/kiln/labs/preload.py:L223` (`build_graph`) and `L286` (`touch`)

- **Look at:** `build_graph` traces only `SAMPLE_RECORDS` records with tracemalloc and extrapolates. The docstring tells the 817 MiB story (errata E-21). Then `touch`: a loop that only *reads*, and still copies 265 MiB per worker in the lab.
- **This code answers the question:** "How can reading cause writes?" Every `record["name"]` takes a reference: incref, then decref, both writes to the object's header.
- **Notice:** the immortal-heavy composition (`_immortal_record`, L176) uses string literals and small ints, which are immortal (gate G3.6), so their refcounts are never written. Lab (b) shows that this saves 45%, not 100%.

## Stop 6 — `src/kiln/memory/gcwatch.py:L256` (A: `_shim_enable`), `L86`/`L157` (B: `_WatchedLoader`, `_ImportFlipFinder`), `L268`/`L332` (C: `_collection_sentinel`, `poll`)

- **Look at:**
  - Layer A replaces the module attribute `gc.enable` (monkeypatching), so it catches only callers that look the attribute up.
  - Layer B wraps *every* module's `exec_module` and compares `gc.isenabled()` before and after. For nested imports it blames the innermost module that flipped the GC (the `child_flipped` flag).
  - Layer C watches the *effect*: the GC found on, or an automatic collection starting while it should be off.
- **This code answers the question:** "Why three layers?" Each one sees something the others can't (the table in the module docstring). Lab (c) confirmed every cell of that table.
- **Notice:** the module imports nothing from Kiln (K7 loads it by file path). Logging happens in `gcmodes.log_gc_event`.
- **Tested by:** `tests/unit/test_gcwatch.py`, including "uninstall restores everything" and "imports still work" (namespace package, zip import, `_json`).

## Stop 7 — `src/kiln/memory/exittrick.py` and `src/kiln/worker/__main__.py:L58-L66`

- **Look at:** `install()` registers the handler *early* so it runs *last* (atexit is LIFO). `_os_exit_with_code` flushes stdout and stderr itself, because `os._exit` won't.
- **This code answers the question:** "What exactly does Instagram's trick skip?" Everything after the atexit handlers: the final collection and module teardown. Lab (d) measured it: 817 ms → 11 ms for a spawned worker with a 300 MiB graph.
- **Tested by:** `tests/integration/test_exit_trick.py`. Read its module docstring and errata E-23 to see why the probe is a garbage cycle created at exit, not a `__del__` at module teardown.

## Stop 8 — `labs/k3/k3_lab.py:L184` (`on_every_worker`), `L221` (`snapshot`), `L255` (`run_phases`)

- **Look at:** the phase protocol: submit 2 × workers jobs, check the returned pids cover every worker, retry up to 5 rounds. The `hold_ms` trick (ADR-036 §3) is what makes the burst spread.
- **This code answers the question:** "How do you measure a server's memory without disturbing it?" From outside: `snapshot` reads `/proc` in the driver process, and `sampler.py` is a third process.

## Checkpoint quiz

1. Why does `collect()` in `memtable.py` use the process tree instead of the command line to tell a forked worker from its master?
   <details><summary>Answer</summary>

   fork copies the whole process, including `argv`, so a forked worker's `/proc/<pid>/cmdline` is identical to the master's. Only its position in the tree (a child of the master) tells them apart. Spawned workers and the forkserver do have their own command lines (`-m kiln.worker`, `kiln.launch.forkserver_main`).

   </details>
2. Why must `apply_parent_early` run before the preload graph is built, not just before fork?
   <details><summary>Answer</summary>

   A collection while the graph is being built would free temporary objects inside pages that also hold graph objects, leaving holes. The workers would later fill those holes with their own new objects, writing to shared pages. Disabling the GC first means the graph's pages are packed and stay untouched until fork.

   </details>
3. Layer B blames the innermost import that flipped the GC. How does `_WatchedLoader.exec_module` know a nested import already took the blame?
   <details><summary>Answer</summary>

   Each `exec_module` pushes a frame onto the watch's `_import_stack`. When an inner import finds a flip, it reports it and sets `child_flipped` on its parent's frame. The parent, on finishing, sees the GC flipped during its own execution too, but skips reporting because `child_flipped` is set.

   </details>
4. Why does the exit trick flush stdout and stderr itself?
   <details><summary>Answer</summary>

   Normally the interpreter flushes Python's output buffers during finalization. `os._exit` ends the process immediately, skipping that, so any text still in a buffer would be lost.

   </details>
5. What would `kiln mem` show for Σ RSS and Σ PSS right after the eight `touch_preloaded` jobs above, compared with before them?
   <details><summary>Answer</summary>

   Σ RSS stays about the same: every page was already resident and counted, shared or not. Σ PSS rises sharply (in the lab, from 389 to 1,451 MiB with 4 workers), because pages that were divided five ways are now separate private copies counted once each.

   </details>
