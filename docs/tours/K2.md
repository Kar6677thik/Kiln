# Code Tour — K2: Start methods (fork / spawn / forkserver) and `kiln forkcheck`

> **Commit:** the final commit of branch `milestone/k2-start-methods` (line numbers below match it) · **Time needed:** ~2 h for the tour, plus the K2 primers · **Milestone spec:** [K2](../milestones/K2-start-methods-forkcheck.md) · **Lab report:** [K2](../labs/K2-forkcheck.md)

K2 has two halves. In the first, Kiln learns to create workers three ways and hides the difference behind one small interface. In the second, we build a tool that reads *other people's* code and points at places that only work because of fork. Follow a worker through each launcher first, then follow one finding (FA002, the oslo.concurrency bug) from source text to a confirmed report.

## The map

```
  master/supervisor.py: launch() ──WorkerLaunchSpec──▶ launcher.launch(spec)
        │                                              (launch/__init__.make_launcher picks one)
        ├─ fork       launch/fork.py        os.fork() ─────────────▶ worker/main.run_worker(app)
        ├─ spawn      launch/spawn.py       os.posix_spawn("python -m kiln.worker --fd N …")
        │                                        └─▶ worker/__main__.main ─▶ run_worker(app=None)
        └─ forkserver launch/forkserver.py  send_fds(spawn_worker + fd) ──▶ Pending
                         │                                  ▼
                         │       launch/forkserver_main.py  ForkServer (a clean helper process)
                         │            fd FIFO ─▶ fork_child ─▶ worker
                         ◀── spawned{pid} / child_exit{wait_status} ──┘
  arbiter: launcher socket readable ─▶ supervisor.on_launcher_events ─▶ set_pid / on_exit
  forkserver dies ─▶ supervisor.on_server_died ─▶ orphans watched by pidfd ─▶ on_orphan_exit

  kiln forkcheck PATH ─▶ forkcheck/__init__.main ─▶ scanner.scan
        ─▶ symbols.build_module (ast + symtable: aliases, guard, scopes, ProcSites)
        ─▶ rules.check_fa001 … check_fa008 ─▶ report (text / JSON)
        └─ --confirm ENTRY ─▶ confirm.confirm_entry: run under fork, forkserver, spawn; compare
```

## Stop 1 — `src/kiln/launch/base.py:L98` (`Launcher`)

- **Look at:** the eight members of the Protocol, and the two result types `Launched` (pid known now) and `Pending` (pid arrives later).
- **This code answers the question:** "How can the supervisor not care which start method is used?" It only ever calls these methods. `mypy --strict` checks that all three launchers match.
- **Notice:** `reaps_children`. Fork and spawn workers are the master's children; forkserver workers are the *server's* children, so the master can't `waitpid` them. That one boolean is the deepest difference between the methods.

## Stop 2 — `src/kiln/launch/spawn.py:L32` (`worker_command`) and `L99` (`SpawnLauncher.launch`)

- **Look at:** the argv list: `sys.executable -m kiln.worker --fd N --worker-id … --config-json …`. Then `os.set_inheritable(fd, True)` right before `posix_spawn`.
- **This code answers the question:** "How does a brand-new interpreter get its socket and its settings?" Its socket is *inherited* (PEP 446 makes fds non-inheritable by default, so we opt this one in), and its settings come as text on the command line.
- **What would break without it:** without `set_inheritable`, the child's `--fd 7` would name a closed fd. Gate G2.2 (`test_worker_fds_are_only_its_own`) proves the opposite holds too: *only* that fd is inherited.
- **Notice:** `posix_spawn`, not `subprocess.Popen`. Popen keeps its own records of its children and may reap them itself, racing with the master's `waitpid(-1)`.

## Stop 3 — `src/kiln/worker/__main__.py:L28` (`main`)

- **Look at:** `socket.socket(fileno=args.fd)` wraps an fd we already own, and `run_worker(app=None)` makes the worker import the app itself.
- **This code answers the question:** "What is different about a spawned worker's start?" Only how it gets its inputs. From `run_worker` on, it's the same code as a forked worker.
- **Notice:** it ends with `sys.exit`, not `os._exit`. A spawned worker has no copy of the master's state to protect (ADR-028).

## Stop 4 — `src/kiln/launch/forkserver.py:L66` (`start`) and `L128` (`launch`)

- **Look at:** `start()` posix_spawns `python -m kiln.launch.forkserver_main` and blocks (bounded by `boot_timeout_s`) for `ready`. Then `launch()` makes **one** `socket.send_fds` call carrying both the frame and the fd.
- **This code answers the question:** "How do I give another, already-running process an open socket?" SCM_RIGHTS: the kernel installs a new fd in the receiver that points at the same open socket.
- **Notice:** `launch()` returns `Pending`. The master never waits for the server's reply (ADR-006): the pid arrives later as a `Spawned` event.

## Stop 5 — `src/kiln/launch/forkserver_main.py:L135` (`_on_control`) and `L158` (`_spawn`)

- **Look at:** every read uses `recv_fds`, and the fds go into `self.fd_fifo`. Each decoded `spawn_worker` frame pops the oldest one.
- **This code answers the question:** "Bytes arrive in arbitrary chunks, so how do I know which fd belongs to which frame?" The fd is sent *with* its frame, never after it, so by the time a frame is fully decoded its fd is already in the FIFO.
- **Notice:** `_spawn` passes the server's own fds as `close_in_child`, so the worker doesn't keep the server's control socket open. Then the server closes *its* copy of the worker's channel.

## Stop 6 — `src/kiln/launch/forkserver_main.py:L193` (`_reap`) and `L215` (`_master_gone`)

- **Look at:** `_reap` sends the **raw** wait status in a `child_exit` frame. `_master_gone` runs when the control socket hits EOF: SIGTERM all children, wait up to 5 s, then SIGKILL.
- **This code answers the question:** "Who reaps a worker the master didn't create, and what if the master crashes?" The server reaps and reports. And if the master dies, the server makes sure no worker outlives it by more than ~5 s (AC-2.3, `test_master_death_takes_forkserver_workers_down`).
- **Notice:** the `GOTCHA:` comment at the top on the logger name ([ADR-035](../decisions.md#adr-035) §4). This file runs as `__main__`.

## Stop 7 — `src/kiln/master/supervisor.py:L369` (`on_launcher_events`), `L403` (`on_server_died`), `L474` (`on_orphan_exit`)

- **Look at:** a `Spawned` event fills in the pid and opens a **pidfd** for the worker. A `ChildExit` goes to the same `on_exit` that the master's own reaping uses. When the forkserver dies, every worker that has a pidfd becomes an orphan and its pidfd is handed to the arbiter's selector (`arbiter.py:L1070`, `watch_orphan`).
- **This code answers the question:** "The forkserver is dead, so who tells me when its workers exit?" A pidfd becomes readable when its process exits, even if that process isn't our child, and it can't be fooled by pid reuse. The exit *status* is lost, though, so the death is `unknown_exit` and its jobs `worker_lost`.
- **Tested by:** `test_launchers_e2e.py::test_forkserver_death_orphans_workers_and_restarts`.

## Stop 8 — `src/kiln/forkcheck/symbols.py:L573` (`build_module`) and `L171` (`is_main_guard`)

- **Look at:** one pass collects import aliases (`import multiprocessing as mp`), top-level statements outside and inside the `if __name__ == "__main__":` guard, scopes via `symtable`, and **ProcSites**: every call that creates a process (`Process(...)`, `Pool(...)`, `ctx.Process`, …).
- **This code answers the question:** "How do you find `mp.Process` when it might be spelled `multiprocessing.Process`, `ctx.Process` or `P`?" By resolving names through the aliases first, then matching against the table of process APIs.
- **Notice:** `_collect_symtable` (L303) keeps only `symtable.Function` tables, because 3.14+ adds hidden `__annotate__` tables ([errata E-19](../research/errata.md#e-19-from-314-symtable-scope-lists-also-contain-__annotate__-tables)).

## Stop 9 — `src/kiln/forkcheck/rules.py:L373` (`check_fa002`) and `L308` (`_unpicklable_target`), one rule end to end

- **Look at:** for each ProcSite, the target expression is checked: a `lambda`, a name that `symtable` says is a nested function, a method of a class defined inside a function, or a `functools.partial` wrapping one of those. Then try `kiln forkcheck corpus/real/oslo-lockutils`: the finding names the line (`distilled.py:47`), the qualname with `<locals>`, the start methods it breaks under, and the hint "move it to module level".
- **This code answers the question:** "How can you know something won't pickle without pickling it?" Pickle stores functions *by reference* (module + qualified name). A qualname containing `<locals>` can't be looked up by a fresh process, and that is visible in the source.
- **Notice:** a `get_context("fork")` receiver turns the error into *info*: under fork nothing is pickled.

## Stop 10 — `src/kiln/forkcheck/confirm.py:L301` (`confirm_entry`) and `L261` (`run_method`)

- **Look at:** the entry script runs three times, once per start method, in a fresh process group with a timeout. It starts through `runpy.run_path(entry, run_name="__main__")` after `set_start_method(m)`. The outcome (`ok`, `exception:<Type>`, `signal:<NAME>`, `exit:<n>`, `timeout`) and the normalised output are compared with the fork run.
- **This code answers the question:** "Is the static finding real?" If spawn or forkserver behaves differently from fork, the breakage the rules predicted is real for this run. It doesn't prove *which* finding caused it, as the `CONCEPT(static-vs-dynamic-analysis)` comment explains.

## Checkpoint quiz

1. Why does `SpawnLauncher.launch` call `posix_spawn` rather than `subprocess.Popen`?
   <details><summary>Answer</summary>

   Popen tracks the children it starts and may call `waitpid` on them itself (for example when its `Popen` object is garbage-collected or polled). The master reaps *every* child with `waitpid(-1)` and needs to see each exit status exactly once. `posix_spawn` just returns a pid and leaves reaping to us.

   </details>
2. The forkserver receives the worker's socket as fd 12 although the master sent its fd 9. Is that a bug?
   <details><summary>Answer</summary>

   No. SCM_RIGHTS passes the *open socket*, not the number. The kernel installs it at the lowest free number in the receiver's fd table, which is usually different.

   </details>
3. Why can't the master just `waitpid` a worker after the forkserver dies?
   <details><summary>Answer</summary>

   `waitpid` only works on your own children. The worker's parent was the forkserver; after it died, the worker was re-parented to a subreaper (on WSL, `Relay(...)`) or pid 1. The master watches its pidfd instead and learns *that* it exited, but not how.

   </details>
4. What does forkcheck need `symtable` for that `ast` alone doesn't give?
   <details><summary>Answer</summary>

   Scope facts: whether a name is local, global or free in a function, and which functions are nested. `ast` shows that a `def` sits inside another `def`. `symtable` says which outer names it captures, and whether a function rebinds a module global with `global`, which FA002's message and FA004 rely on.

   </details>
5. `--confirm` reported `differs: true` for pexpect-context, yet that code works under every method. Why?
   <details><summary>Answer</summary>

   The script prints which start method its context uses, and that line differs under spawn. `--confirm` compares output literally: it proves behaviour *changed*, not that something broke. pexpect pins `get_context("fork")`, which FA008 reports only as *info*.

   </details>
