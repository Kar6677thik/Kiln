# Code Tour — K1: Supervisor (master, workers, signals, queue, reload)

> **Commit:** the final commit of branch `milestone/k1-supervisor` (line numbers below match it) · **Time needed:** ~2.5 h for the tour, plus the K1 primers · **Milestone spec:** [K1](../milestones/K1-supervisor.md) · **Lab report:** [K1](../labs/K1-supervisor.md)

K1 is the heart of Kiln: a master process that forks workers, hands them jobs over private sockets, notices every way they can die, and replaces them without dropping work. Follow one job from the bytes on the wire to its result. Then follow a worker from fork to death.

## The map

```
  kiln CLI / bench load                                   (client side)
     │ client.py: KilnClient ── framing.encode_frame ──▶ TCP 127.0.0.1:7340
     ▼
  master process (ONE thread)  master/arbiter.py: Arbiter._loop_once()
     │  selector.select ──▶ listener / signal pipe / client sockets / worker channels
     │     ├─ client frame ──▶ messages.parse_client_request ──▶ jobs.JobTable.submit
     │     ├─ dispatcher.dispatch ──▶ JobTable.start ──▶ worker channel: `run`
     │     ├─ worker frame `result` ──▶ JobTable.succeed / fail_attempt ──▶ wake waiters
     │     ├─ signal pipe (SIGCHLD) ──▶ supervisor.reap ──▶ classify_exit ──▶ respawn
     │     └─ timers.TimerHeap ──▶ job timeouts, heartbeats, boot/retire deadlines
     │
     │ supervisor.launch ──▶ launch/fork.py: fork_worker ──os.fork()──┐
     ▼                                                               ▼
  worker process  worker/main.py: run_worker()                    (one per worker)
     signals reset ─▶ logging ─▶ app ─▶ heartbeat thread ─▶ `ready` ─▶ _receive_loop
     run ──▶ executors/sync.py ──▶ executors/base.run_task(app, run) ──▶ `result`
     exit ──▶ finalize_and_exit ──▶ os._exit(code)
```

## Stop 1 — `src/kiln/protocol/framing.py:L108-L170` (`FrameDecoder`)

- **Look at:** `feed()`. Bytes go into a `bytearray`. The `while` loop takes out a frame only when its 4-byte header *and* its whole body are present; otherwise `break` waits for more bytes.
- **This code answers the question:** "TCP gives me bytes in random chunks. How do I get whole messages?"
- **What would break without it:** any message bigger than one `recv()` (or two messages in one `recv()`) would be misread. `tests/unit/test_framing.py::test_split_at_any_offset_decodes_identically` cuts frames at every possible point to prove this works.
- **Notice:** the length check happens on the header alone (`FrameTooLarge`), so a peer can't make us buffer a gigabyte by lying about the length.

## Stop 2 — `src/kiln/protocol/messages.py:L295-L320` (`_int`) and `L576` (`parse_client_request`)

- **Look at:** `_int` rejects `bool` on purpose: `isinstance(True, int)` is `True` in Python. Then look at how `parse_client_request` uses a dict of parsers instead of a long `if` chain.
- **This code answers the question:** "How does untrusted input become trustworthy data?" Everything after this point receives frozen dataclasses (`Submit`, `Wait`...) whose fields are already checked.
- **What would break without it:** `{"req_id": true}` would be accepted, and a later `req_id + 1` would silently become `2`.

## Stop 3 — `src/kiln/master/jobs.py:L59` (`_ALLOWED`) and `L174` (`_transition`)

- **Look at:** the transition table is *data*: one line per allowed `(from, to)` pair, copied from spec/03 §4.1. `_transition` is the only place a job's state changes, and it refuses anything not in the table.
- **This code answers the question:** "How can I be sure a finished job never changes again?" No path through the code can set `job.state` except through this check.
- **Notice:** `fail_attempt` (L387) holds the whole retry rule in one place: retry only if the failure kind is in `retry_on` *and* attempts remain. Retries go to the back of the queue.
- **Tested by:** `tests/unit/test_jobtable_state_machine.py`. Hypothesis runs 500 random sequences of submits, results, timeouts, cancels and stale results, checking 6 invariants after every step.

## Stop 4 — `src/kiln/master/timers.py:L42-L130` (`TimerHeap`)

- **Look at:** `schedule`, `cancel` (it only remembers the id) and `pop_expired` (it skips cancelled ids). That's lazy deletion: removing from the middle of a heap is slow, skipping at the top is cheap.
- **This code answers the question:** "How does a single-threaded loop do hundreds of different things *later*?" Before each `select()`, the loop asks `next_deadline()` and sleeps at most that long.

## Stop 5 — `src/kiln/launch/fork.py:L45-L140` (`fork_worker`, `_child`)

- **Look at:** the order of operations around `os.fork()`:
  1. Assert the master has exactly one thread.
  2. Create the socketpair.
  3. **Flush buffers.**
  4. Fork.
  5. In the child: close every inherited fd it must not keep, run the worker, and end with `finalize_and_exit` inside `finally`.
- **This code answers the question:** "What does a child inherit, and what must it throw away?"
- **What would break without it:**
  - Without the flush, log lines would be printed twice.
  - Without closing fds, the worker would hold the master's listening port open.
  - Without `os._exit`, the child would *return into the master's code*, and you'd have two masters.
  - Proof: `test_worker_fds_are_only_its_own` and `test_pidfile_survives_worker_deaths`.

## Stop 6 — `src/kiln/worker/main.py:L89` (`_setup_signals`) and `L214` (`run_worker`)

- **Look at:** the worker's first act is to undo what it inherited. `set_wakeup_fd(-1)` matters most: without it, the worker's signals would wake the *master's* loop. SIGINT is ignored (ADR-024), so Ctrl-C reaches only the master's decision-making.
- **Then:** logging is re-configured with `role=worker`, `oom_score_adj` is raised to 500 (ADR-029), the app is loaded, the heartbeat starts, and `ready` is sent with the manifest.

## Stop 7 — `src/kiln/worker/main.py:L282` (`_receive_loop`): the retirement handshake

- **Look at:** when a worker decides to leave (`max_jobs`, `max_rss`, SIGTERM), it sends `retiring` and **keeps serving** until the master answers `shutdown`.
- **This code answers the question:** "How can a worker leave without losing a job that was already on its way?"
- **The story:** the first version exited right after announcing. `test_max_jobs_with_jitter_recycles_between_10_and_15` then lost a job about 1 run in 3. The master had sent one more `run` that crossed the worker's goodbye in flight. Messages on one socket arrive *in order*, so waiting for `shutdown` guarantees that every `run` sent before it is served. ADR-034 records the fix.

## Stop 8 — `src/kiln/worker/channel.py:L61` (`Channel.send`) and `src/kiln/worker/heartbeat.py:L40`

- **Look at:** two threads send on one socket: the main thread (results) and the heartbeat thread. The `Lock` makes each `sendall` of a frame happen whole.
- **What would break without it:** two `sendall` calls could interleave their bytes, and the master would see a corrupt frame and kill the worker (`protocol_violation`).
- **Lab tie-in:** lab (d) shows the heartbeat thread *keeps running* during a pure-Python CPU loop (the interpreter switches threads every 5 ms), but *stops* during `labs.hold_gil`, which is C code holding the GIL.

## Stop 9 — `src/kiln/master/arbiter.py:L363` (`_loop_once`) and `L392` (`_flush_dirty`)

- **Look at:** the loop of spec/01 §4 in about 25 lines:
  1. Compute the timeout from the next timer.
  2. `select`.
  3. Route each ready socket by its `kind`.
  4. Fire expired timers.
  5. Dispatch.
  6. Flush output.
- **This code answers the question:** "How can one thread serve 64 clients and 12 workers at once?" Nothing in it ever waits: every socket is non-blocking, and anything not finished stays in a buffer for the next pass.
- **Notice:** `_flush_dirty` switches a socket's interest to `EVENT_READ | EVENT_WRITE` only while it has unsent bytes. Leaving `EVENT_WRITE` on all the time would make `select()` return instantly forever (a busy loop).

## Stop 10 — `src/kiln/master/signals.py:L39-L105` (`SignalPipe`)

- **Look at:** `_handler` does one thing: `self.pending.append(signum)`. Python's C-level handler has already written a byte to the wakeup socket, which the selector watches.
- **This code answers the question:** "How does a signal turn into an ordinary event?" The real work (`reload`, `begin_shutdown`, `reap`) happens later, in `Arbiter._handle_signals`, at a safe point of the loop.

## Stop 11 — `src/kiln/master/supervisor.py:L77` (`classify_exit`), `L508` (`reap`) and `L526` (`on_exit`)

- **Look at:** `os.WIFEXITED` / `WEXITSTATUS` / `WTERMSIG` turn one number into a cause of death. The key row: a SIGKILL that *we* didn't send (`kill_sent is None`) is "suspected OOM", and `_oom_evidence` checks the cgroup's `oom_kill` counter to confirm it.
- **Notice `drain_worker` in `on_exit`.** This is the second bug a test found (`test_reload_under_load_drops_nothing`, about 1 run in 3). A worker sends its last result and exits, and the loop may handle SIGCHLD before reading that worker's socket. The finished job was then declared `LOST`. The fix is to read everything left in a dead worker's channel before resolving its jobs. The bytes are still in the kernel's socket buffer, even after the process is gone.

## Stop 12 — `src/kiln/master/supervisor.py:L832` (`reload`) and `L489` (`_retire_one_old`)

- **Look at:** a reload bumps the generation and launches `target` new workers. Each time one becomes READY, the old worker with the fewest jobs is retired.
- **This code answers the question:** "How can every worker be replaced while jobs keep flowing?" The queue never moves, because it lives in the master (ADR-007), and retiring workers finish what they hold. Lab (b) measured this under 10,000 jobs with a reload every 2 seconds.

## Checkpoint quiz

1. After `pid = os.fork()`, how many processes run the next line? What is `pid` in each?
   <details><summary>Answer</summary>

   Two. In the parent, `pid` is the child's process id (a positive number). In the child it is `0`. That's the only way each copy knows which one it is. See [fork](../concepts/fork.md).

   </details>
2. Why does the master forbid threads, but workers may start a heartbeat thread?
   <details><summary>Answer</summary>

   `fork()` copies only the calling thread. If another thread held a lock (for example inside logging) at that moment, the child inherits the lock *held*, with no thread left to release it, and deadlocks. The master forks, so it must have no threads (ADR-006). Workers never fork, so they may use threads; they start the heartbeat *after* the fork. See [fork-and-threads](../concepts/fork-and-threads.md).

   </details>
3. A worker's `waitpid` status says "terminated by signal 9", and `kill_sent` is `None`. What do we log, and why only "suspected" OOM?
   <details><summary>Answer</summary>

   `worker_died how=killed signal=SIGKILL suspected_oom=true`, plus an `oom_evidence` field. SIGKILL can't be caught, and the kernel's OOM killer uses it, but anyone (`kill -9`, `labs.crash sigkill_self`) can send it too. Only the cgroup's `oom_kill` counter going up *confirms* an OOM kill. Lab (a) shows both cases.

   </details>
4. Why does a TCP `recv(4096)` sometimes return half a message? How does `FrameDecoder` cope?
   <details><summary>Answer</summary>

   TCP is a byte stream with no message boundaries, so a recv returns whatever bytes have arrived. The decoder keeps leftover bytes in a buffer and only returns a message once its 4-byte length and its whole body are there.

   </details>
5. What would go wrong if the signal handler itself called `supervisor.reload()`?
   <details><summary>Answer</summary>

   Python runs handlers between two bytecodes of whatever the main thread was doing. That might be halfway through updating the job table or a worker's in-flight set, and reload would act on half-updated state. Recording the signal and acting at a known safe point in the loop avoids that.

   </details>
6. During a SIGHUP reload, where are queued jobs, and why aren't any lost?
   <details><summary>Answer</summary>

   In the master's `JobTable.queue`. They never leave the master until dispatched. Old workers are retired only one at a time, as new ones become READY, and a retiring worker finishes its in-flight jobs and drains its channel. Lab (b): 0 lost jobs across 30,000 jobs and the reloads during them.

   </details>
7. Why does `max_jobs_jitter` exist?
   <details><summary>Answer</summary>

   Workers started together would hit `max_jobs` together and all restart at once, dropping capacity to zero for a moment. A random extra 0..jitter jobs per worker spreads the restarts out.

   </details>
8. Why does a pure-Python infinite loop *not* stop heartbeats on the GIL build, but a GIL-holding C call does? What changes on 3.15t?
   <details><summary>Answer</summary>

   The interpreter forces a thread switch every `sys.getswitchinterval()` (5 ms) while running Python bytecode, so the heartbeat thread gets turns. C code that keeps the GIL (`ctypes.PyDLL`, a backtracking regex) never gives it up. On 3.15t there is no GIL, so threads run truly in parallel and the heartbeat continues (lab d: max silence 1.0 s).

   </details>
9. What is a zombie process? What happens if the master never calls `waitpid`?
   <details><summary>Answer</summary>

   A dead child whose exit status hasn't been collected; the kernel keeps a small record until the parent reaps it. Without `waitpid` the zombies pile up, the master never learns how workers died, and it never replaces them.

   </details>
10. Why do workers ignore SIGINT?
    <details><summary>Answer</summary>

    Ctrl-C sends SIGINT to the whole foreground process group, which includes every worker. If workers died on it, a single Ctrl-C would kill running jobs before the master could do a graceful shutdown (ADR-024).

    </details>
11. With `max_attempts=3`, could a task's side effect happen twice? When?
    <details><summary>Answer</summary>

    Yes. If the worker does the side effect (sends an email) and then dies before reporting, and `worker_lost` is in `retry_on`, attempt 2 sends it again. That's at-least-once delivery, so only use retries for idempotent tasks. See [delivery-semantics](../concepts/delivery-semantics.md).

    </details>
12. Why is RSS summed over all workers larger than the real memory used?
    <details><summary>Answer</summary>

    RSS counts every page a process uses, including pages shared with other processes through copy-on-write after fork. The same shared page is counted once in *every* worker. K3 measures PSS, which divides shared pages fairly.

    </details>
